# 02. Architecture: layout, boundaries, where code goes

## 1. The shape of the system

One Next.js app, one Postgres database, no separate backend service. Four workspace packages hold everything that is not specific to the web app, so the schema, the database, the AI prompts and the templates can each be read and tested alone.

```
folix/
  apps/
    web/                     the Next.js app (the only deployable)
  packages/
    schema/                  Zod schemas, types and product limits. No dependencies on other packages.
    db/                      Drizzle tables, migrations, query functions. Depends on schema.
    ai/                      Prompts, generation, extraction, interview logic. Depends on schema.
    templates/               Portfolio template components, theme tokens, registry. Depends on schema.
  tooling/
    eslint-config/           Shared lint rules (each one enforces a rule in docs/rules)
    tsconfig/                Shared TypeScript settings
  docs/                      product, planning, rules, design, engineering, decisions
  scripts/                   repo checks
```

**Dependency direction (never the other way):**

```
schema  <-  db
schema  <-  ai
schema  <-  templates
schema, db, ai, templates  <-  apps/web
```

- `schema` imports nothing from the workspace. It is the source of truth.
- `db`, `ai` and `templates` never import each other and never import from `apps/web`.
- Packages never read environment variables. The app validates its env once (`apps/web/src/env.ts`) and passes values in (`createDb(url)`).
- Packages export TypeScript source and are compiled by Next (`transpilePackages`). There is no package build step.

## 2. The web app

```
apps/web/src/
  app/                       routes only. Thin: read params, call server functions, render components.
    (marketing)/             public marketing pages, shared header and footer
    (auth)/                  login
    app/                     the signed-in product, URL /app/...
    [slug]/                  public portfolio pages (from Milestone 2)
    api/                     route handlers: auth, health, AI streaming, uploads, events
  components/
    ui/                      shadcn/ui primitives, generated by the CLI, kept close to upstream
    shared/                  our own components used across features
    layout/                  page structure: Container, SectionHeading
    brand/                   logo
    <feature>/               components for one feature: marketing, auth, app, editor, intake
  server/                    server-only code. Every file starts with `import 'server-only'`.
    auth/                    auth config, session helpers (requireUser)
    db.ts                    the database client
    email/                   outgoing email
    <feature>/               data functions and server actions for one feature
  lib/                       small pure helpers, usable on server and client
  config/                    ROUTES, SITE
  content/                   marketing copy as data
  hooks/                     shared client hooks
  env.ts                     the only reader of process.env
```

## 3. Where code goes

| You are writing                                     | It goes in                                                     |
| --------------------------------------------------- | -------------------------------------------------------------- |
| A content shape, a validation rule, a product limit | `packages/schema`                                              |
| A table, an index, a query                          | `packages/db`                                                  |
| A prompt, model call, extraction or generation step | `packages/ai`                                                  |
| A portfolio template or theme token                 | `packages/templates`                                           |
| A business rule that touches the database and auth  | `apps/web/src/server/<feature>/`                               |
| A mutation the UI calls                             | A server action in `apps/web/src/server/<feature>/*.action.ts` |
| A stream, upload, webhook or third-party callback   | A route handler in `apps/web/src/app/api/`                     |
| A screen                                            | `apps/web/src/app/.../page.tsx`, built from components         |
| A reusable piece of UI                              | `components/<feature>/` or `components/shared/`                |
| A pure helper                                       | `lib/` (app) or the owning package                             |
| An internal URL                                     | `config/routes.ts`. Never a string literal in a component.     |
| Marketing wording                                   | `content/marketing.ts`                                         |

**The layering inside a feature:**

```
page.tsx  ->  component  ->  server action  ->  feature function  ->  db query
(route)      (UI)           (validate, authorise,    (the rule)        (storage only)
                             map errors)
```

- **Pages hold no logic.** They read params, call a server function, and lay out components.
- **Components hold no data access.** Server components may call a feature read function. Client components receive data through props and call server actions.
- **Server actions are thin adapters:** validate input, authorise, call the feature function, map the result to `ActionResult`, revalidate. The rule itself lives in the feature function, so it can be tested without HTTP.
- **Query functions do storage only.** No business rules in `packages/db`. No SQL outside it.
- **Pure rules are pure.** A function that decides something (is this slug valid, which fields are locked, what is missing from a profile) takes inputs and returns outputs. No database, no clock, no network. This is what makes it testable.

## 4. Single sources of truth

| Truth                         | Lives in                                          |
| ----------------------------- | ------------------------------------------------- |
| Content shapes and validation | `packages/schema` (Zod), used by forms, db and AI |
| Product limits                | `packages/schema/src/limits.ts`                   |
| Slug rules and reserved slugs | `packages/schema/src/slug.ts`                     |
| Table definitions             | `packages/db/src/schema/`                         |
| Environment variables         | `apps/web/src/env.ts`                             |
| Internal URLs                 | `apps/web/src/config/routes.ts`                   |
| Colours, type, radius, motion | `apps/web/src/app/globals.css`                    |
| Prompts                       | `packages/ai`                                     |
| A user's facts                | `profiles.content` (the master profile)           |
| What the public sees          | `portfolios.published_content` (the snapshot)     |

Never store what can be derived. Never copy a truth into a second place: import it.

## 5. Where state lives

| Kind of state                                  | Where                                                      |
| ---------------------------------------------- | ---------------------------------------------------------- |
| Saved data                                     | Postgres. Read on the server, passed down as props.        |
| What is in the URL (tab, step, filter, `next`) | The URL: route params and search params                    |
| Form input before submit                       | The form (`useActionState`, or `useState` for small forms) |
| Short-lived UI state (open, hover, pending)    | `useState` in the component                                |
| State shared by a subtree (editor selection)   | React context scoped to that subtree                       |
| Server data on the client                      | Not duplicated. Re-read on the server after a mutation.    |

- **No global client store by default.** Add one (Zustand) only when a concrete feature needs cross-tree client state that context handles badly, and record the decision.
- **Never mirror server data into client state** to "keep it handy". Two copies drift.
- A user must be able to refresh on any step and land in the same place. If refresh loses the step, the step belongs in the URL or the database.

## 6. Adding to the system

- **A new environment variable:** add it to `env.ts`, `.env.example`, `turbo.json` (build `env`), the CI workflow if the build needs it, and `docs/engineering/environment.md`.
- **A new top-level route:** add it to `ROUTES` and to `RESERVED_SLUGS`. A test fails if you forget the second.
- **A new table:** see [04-backend.md](04-backend.md), "Database".
- **A new dependency:** it must solve a problem the current stack cannot. Check its size, maintenance and licence, pin it through the pnpm catalog if two packages use it, and record it in DECISIONS.md when it is a new kind of thing (a state library, a new service).
- **A new package:** only when code has a second consumer or needs to be tested apart from the app. Not for tidiness.
